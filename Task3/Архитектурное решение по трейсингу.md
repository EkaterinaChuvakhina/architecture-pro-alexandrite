### 1. Системы, которые следует покрыть трейсингом  
 
1. REST-запросы в backend (Shop API, CRM API, MES API)
   Заказ может "зависнуть" на обработке запросов по разным причинам, например, timeout, баг в коде, проблемы с бд и др.
2. Обработка и отправка сообщений в RabbitMQ 
   Задержки в очередях, потери сообщений при росте нагрузки или при ошибках обработки.
3. SQL-запросы к БД (Shop DB, MES db)
   Медленное выполнение запросов на запись/чтение из-за перегрузки БД, неверно настроенных блокировках, технических ошибок бд инфраструктурных проблем.

#### Данные трейсинга

1. Общие данные трейсинга
   - Trace ID 
   - Span ID
   - Timestamp
   - Duration
   - Operation Name
   - Status Code
   - Error Details  

2. Данные для REST-запросов/ответов
   - HTTP Method и URL
   - Request/Response Headers
   - Order ID: ID заказа, нужен для трассировки по конкретному заказу
   - User ID/Type: ID пользователя и тип, нужен для разделения B2B/B2C  

3. Данные для обработки/отправки сообщений в RabbitMQ
   - Queue Name  
   - Routing Key
   - Message Size
   - Operation Type: "Publish" или "Consume"
   - Order ID: ID заказа, нужен для трассировки по конкретному заказу

4. Данные для SQL-запросов (Shop DB, MES db)
   - SQL Statement
   - Database
   - Table Name
   - Query Type
   - Rows Affected

5. Данные для S3 запросов
   - Operation Type
   - Bucket
   - Key
   - Size: размер файла

### 2. Мотивация
Трейсинг необходим для повышения наблюдаемости системы, чтобы понять, где задержки заказов возникают из-за скрытых проблем в backend, RabbitMQ, БД и S3.
Трейсинг дает полную видимость цепочки операций, показывая точный путь запроса через сервисы, позволяя быстро находить причины задержек, что сократит время на решение проблем и
сделает систему более устойчивой и масштабируемой. 

### Метрики, на которые влияет внедрение трейсинга
1. Average Response Time 
Трейсинг позволяет точно определить, какой именно компонент вызывает деградацию общего времени отклика, благодаря отображению цепочки вызовов при запросе.
2. Error Rate
Трейсинг позволяет определить, в каком именно сервисе и на каком участке кода возникла проблема
3. Infrastructure Cost Allocation
Трейсинг позволяет определить, какие бизнес-процессы являются наиболее ресурсоемкими. Это дает основу для оптимизации 
 затрат на облачную инфраструктуру и обоснование для рефакторинга дорогих функций.
4. Time to Resolution
Трейсинг значительно сокращает время от обнаружения до решения инцидента. Ускоряет отладку, минимизируя потери.

   
### 3. Предлагаемое решение
Трейсинг будет реализован с помощью OpenTelemetry (OTel) — открытого стандарта для трассировки, OTel интегрируется с backend приложениями и позволяет автоматически захватывать данные о запросах (REST, RabbitMQ, SQL, S3), добавляя минимальный overhead. 
Для визуализации будет использоваться Jaeger. OTel Collector — промежуточный сервис для сбора и экспорта трасс в Jaeger.

### 4. Компромиссы

#### Случаи, где трейсинг не принесет существенной пользы

1. Монолитные системы с низкой нагрузкой - для простого приложения с небольшим числом интеграций будет достаточно централизированого сбора логов и метрик 
, а внедрение трейсинга будет избыточным.
2. Ultra-low latency - трейсниг добавляет дополнительные расходы, например на генерацию span, добавление контекста, отправку в коллектор).
В системах, где важна каждая микросекунда эти расходы могут быть неприемлемы. 
3. В системах с жёсткими ограничениями на потребление ресурсов
Агенты трейсинга потребляют CPU, память и сетевой трафик. В условиях строгого лимита на потребление внедрение трейсинга может быть невозможно
4. MVP
Для просты систем для тестирования гипотез, внедрение трейснга может быть сложным и не оправданным.
5. Проприетарные системы - системы код которых нельзя модифицировать или интеграция с системой с жестким API, который не поддерживает заголовки трейсинга 

### 5. Меры для предотвращения несанкционированного доступа

1. Строгое управление доступом к UI Grafana (или Jaeger UI)
Использование RBAC и соблюдение принципа минимальных привилегий 
2. Аудит действий 
Все действия сотрудников логгируются, особый контроль к поиску по конфиденциальным данным пользователей
3. Использование mTLS между агентами
4. Шифрование данных
Все данные в хранилище должны быть зашифрованы 
5. Маскирование персональных данных
