### 1. Текущие и потенциальные проблемные места 

1. Отсутствие мониторинга и алертов для бизнеса и инфраструктуры  
   О проблемах первыми узнаю клиенты и менеджемент, а не команда поддержки и разработки
2. Перегруженность обязанностями backend MES  
  Backend MES отвечает за:  
   - дашборд для операторов(просмотр заказов, назначение заказов на операторов)
   - расчет стоимости заказа
   - обновление статуса заказа
   - обработку заказов через RabbitMQ и API для B2B
   - отправку изменений статуса заказа через RabbitMQ
3. Медленный расчет стоимости и недостаточное масштабирование MES  
   Расчет стоимости заказа в MES занимает от 2 до 30 минут и выполняется на одном инстансе,  
   что создает узкое место при росте заказов
4. Высокая нагрузка на БД MES и недостаточное масштабирование  
   БД MES перегружена запросами на запись и чтение при обновлении статусов заказов, обновление информации о назначении операторов и запросах на отображение дашборда для операторов
5. Отсутствие разделения нагрузки между B2C и B2B трафиком  
   CRM и онлайн-магазин используют одну БД для пользовательских и партнерских заказов, B2B-заказы поступают напрямую в MES через API нет изоляции ресурсов для разных типов трафика
6. Распределение изменений статусов по разным системам  
   Статусы заказов обновляются в разных компонентах (интернет-магазин, MES, CRM, транспортная компания) с синхронизацией через RabbitMQ и БД, без гарантий согласованности
7. Потенциальная перегрузка доступа к S3 в MES  
   Все расчеты зависят от чтения 3D-моделей из S3, без упоминания кеширования или оптимизации под высокую нагрузку  
8. Ручной деплой в release и prod окружения  
   Медленный релиз фич и фиксов, риск человеческих ошибок, несоответствия окружений
9. Отсутствие контейнеризации и оркестрации  
   Приложения развернуты напрямую на ВМ, что приводит к несогласованности окружений, ручному управлению зависимостями, ограниченной масштабируемости



### 2. Инициативы, которые необходимы для устранения нежелательных ситуаций

1. Внедрить мониторинг и настроить алерты - поможет диагностировать узкие места и найти причины потерь клиентов. 
2. Настроить кеширование для дашборда в MES - снижение нагрузки на БД MES, низкая сложность реализации, но заметное улучшение пользовательского опыта. 
3. Разделить трафик B2B и B2C - разделение очередей, инстансов приложения MES, БД поможет улучшить производительность, снизив жалобы от партнёров и клиентов.
4. Настроить backpressure в RabbitMQ для снижения нагрузки на расчёты - замедлит поток заказов, если MES не справляется с расчётами, предотвращая перегрузку.
5. Увеличить число инстансов MES и оптимизировать доступ к S3 - позволит ускорить получение 3D-моделей из S3 и увеличить пропускную способность при росте заказов, что может уменьшить время расчета стоимости заказа.
6. Разделение монолита MES на микросервисы - выделить сервисы (расчёт стоимости заказа, дашборд для операторов, сервис для обработки заказов внешних клиентов), разделит обязанности, упростит масштабирование отдельных частей.
7. Переход c RabbitMQ на Kafka и внедрение event sourcing для статусов заказов - устранит несогласованность и дублирование данных между БД. Переход на Kafka с pull моделью снизит нагрузку на сервис расчета стоимости.
8. Автоматизировать CI/CD и внедрить контейнеризацию - ускорение релизов, снижение ошибок из-за ручного деплоя и разных окружений.


### 3. Целевая архитектура через полгода

Переход от монолита MES к микросервисам — отдельные сервисы для расчета стоимости, дашборда операторов, API для партнеров.  
Kafka как основной message broker с pull-моделью для контроля нагрузки. Event sourcing для статусов заказов — все изменения как события в Kafka, без дублирования БД.
Отдельные сервисы и ресурсы для B2B и B2С. Все приложения в Docker-контейнерах, оркеструемые Kubernetes, для БД кеширование в Redis. S3 с CDN для быстрого доступа к 3D-моделям.
Aвтоматизированный CI/CD. Настроен мониторинг и алерты для метрик чтобы вовремя выявлять перегрузки и другие проблемы системы.

### 4. Если бы у вас была возможность выполнить только три пункта из списка инициатив в ближайшие полгода, что бы вы выбрали и почему?

1. Внедрить мониторинг и настроить алерты - поможет видеть массовые сбои и в моменте исправить ситуацию, 
   косвенно улучшит безопасность системы, надежность, производительность и пользовательский опыт. 
2. Разделить трафик B2B и B2C - значительно улучшит производительность системы, средняя сложность реализации, влияет, и на B2B партнеров и на B2C.
3. Разделение монолита MES на микросервисы - позволит улучшить опыт использования для всех пользователей системы и снизить затраты на облако за счет гибкого масштабирования узких мест, 
   увеличить надежность и уменьшить риск сбоя дашбода для операторов и API для партнеров, т.к сложные расчеты стоимости заказа могут тормозить остальные операции.
