### Типы логов, которые нужно собирать:

- Логи бизнес-логики: Записи о ключевых событиях, таких как создание/изменение заказа, расчёт стоимости. Уровни: INFO для нормальных событий, WARN/ERROR для проблем.
- Логи доступа: Записи о входящих и исходящих запросах к API.
- Производительные логи: Логи времени выполнения операций (например, расчёт цены, загрузка дашборда).
- Аудит-логи: Изменения статусов заказов, действия пользователей (клиентов, операторов, менеджеров).
- Логи очередей: Сообщения, отправленные/полученные в RabbitMQ.
- Базы данных и хранилища: логи запросов к БД из приложений и для S3 — логи загрузки/доступа. 

#### Cписок необходимых логов с уровнем INFO.
- Вход/выход REST-запроса (backend-сервисы): Логируем timestamp, метод, URL, order_id, user_id или system_id
- Создание заказа (Shop API, CRM API): Логируем timestamp, order_id, user_id, source (B2C или B2B)
- Подтверждение заказа (CRM API): Логируем timestamp, order_id, approved_by, client_type (B2C или B2B)
- Начало расчёта стоимости (MES API): Логируем order_id, timestamp
- Завершение расчёта стоимости (MES API): Логируем order_id, calculated_price, timestamp
- Назначение заказа оператору (MES API): Логируем order_id, operator_id, assignment_time, timestamp
- Получение подтверждения от транспортной компании (CRM API): Логируем order_id, delivery_status, timestamp
- Загрузка дашборда (MES API): Логируем user_id, filter, load_time, order_count_displayed, timestamp
- Изменение статуса заказа (CRM API, MES API): Логируем timestamp, order_id, user_id, old_status, new_status
- Publish сообщения в RabbitMQ (CRM API, MES API): Логируем timestamp, queue_name, routing_key, order_id, message_type
- Сonsume сообщения из RabbitMQ (CRM API, MES API): Логируем timestamp, queue_name, order_id, message_type

#### Другие уровни логирования
- DEBUG - для логирования внутренних операций, переменных или данных, которые не нужны в повседневном мониторинге, но могут помочь
при расследовании сложных проблем, например: детали запроса к БД, детали алгоритма расчета, payload сообщения из RabbitMQ.

- WARN - событие не критично, но указывает на потенциальную проблему или неоптимальное поведение, например: несколько неудачных попыток авторизации, 
много заказов от одного пользователя, необработанное сообщение RabbitMQ.

- ERROR - при ошибках, которые влияют на работу, но система продолжает функционировать, например, ошибка расчёта стоимости,  
сбой интеграции RabbitMQ, Ошибка при REST запросе, проблема с БД.

### Мотивация 
Внедрение логирования принесёт компании следующие преимущества: 
- Отладка и диагностика — быстрая идентификация и исправление ошибок в системе
- Мониторинг производительности — отслеживание работы системы в реальном времени
- Анализ инцидентов — восстановление последовательности событий при сбоях
- Аудит безопасности — обнаружение подозрительной активности и расследование инцидентов
- Анализ пользовательского поведения — понимание того, как клиенты взаимодействуют с системой

### Метрики, на которые влияет внедрение логирования
1. Uptime 
Логирование фиксирует события, приводящие к простоям, такие как ошибки в коде, перегрузки ресурсов или сбои интеграций 
и позволяет настроить алерты на критические события, что даёт возможность вовремя заметить массовые сбои и быстро среагировать на проблему. 
Также, анализ логов помогает предотвращать повторные инциденты.
2. Incident Response Time
 Логирование позволяет быстро обнаружить проблему с помощью алертов, анализ логов помогает быстрее разобраться с проблемой.
3. Error Rate
Логи фиксируют ошибки и исключения, позволяя определить частоту их возникновения и причины 
3. Customer Satisfaction 
Логи фиксируют действия пользователей и состояние системы, помогая объяснить причины жалоб пользователей, 
плюс помогают решать проблемы до того как они станут видны пользователям 

### Для каких систем нужно настраивать логирование и трейсинг в первую очередь и почему.
В первую очередь необходимо внедрить логирование для бизнес-сценариев backend-сервисов и обработке/публикации событий из очереди - 
логи/трейсинг дадут видимость выполнения пользовательских сценариев и помогут определить, причины задержки заказов, что значительно улучшит пользовательский опыт.

Вторым приоритетом добавлять логирование для frontend и БД 

### Предлагаемое решение
1. Для Spring Boot (Shop API, CRM API): Будет использоваться SLF4J с Logback. Logback поддерживает асинхронное логирование для минимизации влияния на производительность. 
Добавим конфигурацию для structured logging с JSONLayout (библиотека logstash-logback-encoder). Уровни логирования будут динамически настраиваться через Spring Actuator.
2. Для C# (MES API): Применяем Serilog как основную библиотеку, с поддержкой structured logging и JSON-форматирования. Интегрируем Serilog.Sinks.Async для асинхронности.
3. OTel Collector будет собирать логи из приложений 
4. В качестве ценрализованного хранилища логов будет использоваться OpenSearch
5. Kibana - для визуализации 

### Необходимые мероприятия для превращения системы сбора логов в систему анализа логов

1. Маскирование - обязательно для всех чувствительных данных, можно реализовать из приложения.
2. Отсутствие персональных данных в логах на проме, только для отладки на dev стендах. 
3. Строгое управление доступом к UI Kibana/Logstash (или Jaeger UI)
Использование RBAC и соблюдение принципа минимальных привилегий 
4. Аудит доступа: Каждый запрос к Kibana/OpenSearch логируется


Структура хранения: отдельные индексы в OpenSearch по сервисам (shop-, crm-, mes-) и окружениям (dev-, prod-).

Retention periods:  
INFO/WARN: 60 дней достаточно для оперативного анализа  
ERROR/FATAL: 180 дней для анализа истории ошибок  
Audit/Security logs: 1-3 года, зависит от политики компании   

### Нужно ли настроить какой-то алертинг? 
Алертинг обязательно нужно настроить, например Splunk.
Алертинг превращает систему в проактивную: он уведомляет команду о проблемах в реальном времени, минимизируя ущерб. 

Почему это важно для компании:
- Алертинг на основе логов позволит фиксировать их командой поддержки, до обнаружения пользователями.
- Рост нагрузки (+100 заказов/месяц) увеличивает риски — алертинг предотвратит перегрузку системы.
- Без алертинга логи не так эффективно помогают обнаруживать проблемы, анализ вручную занимает много времени, что приводит к оттоку клиентов.

Также нужно обязательно искать аномалии, с этим особенно эффективно справляются Ml инструменты, например, OpenSearch ML
