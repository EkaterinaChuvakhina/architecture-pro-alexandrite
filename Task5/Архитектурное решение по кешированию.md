
### Мотивация 
Кеширование — это относительно простая инициатива, которая даст быстрый эффект на производительность, без радикальных изменений в архитектуре.  

Нужно внедрить кеширование для сервиса MES.
Необходимо внедрить серверное кеширование, т.к основные проблемы связаны с общей нагрузкой на backend и базу данных PostgreSQL системы MES,
где данные о заказах, их распределении по операторам, статусах с точки зрения MES и расчетах для пользователей (операторов, API-клиентов, клиентов интеренет-магазина).
С увеличением заказов и подключением к API партнеров MES, чтение данных из БД сильно замедлилось.
Серверное кеширование позволит централизованно управлять кешем, снижая количество прямых обращений к БД для чтения данных, ускорив загрузку дашборда.

### Предлагаемое решение

Комбинация Write-Through + Read-Through

Write-Through гарантирует, что при любом обновлении (новый статус заказа через RabbitMQ) кеш сразу синхронизируется с БД. 
Операторы увидят самые свежие данные — нет риска "старого" кеша, как в Cache-Aside. Но не помогает с чтением, когда в кеше еще нет записи.

Read-Through устраняет задержки от при пустом кеше: первый раз дашборд загружает из БД и сохраняет в кеш; потом — мгновенно из кеша. Минимизирует количество кеш-промахов.
В итоге: Комбинация двух подходов позволяет достигнуть баланса скорости и актуальности данных.

### Инвалидация кеша 

Выбор стратеги Write-Through обеспечивает актулальность данных кеша.
Данные между кешем и базой данных всегда будут синхронизированы. Это исключает возможность неконсистентности кеша и его инвалидацию, но только если исключены ручные изменения в бд.

Если ручные изменения допускаются, то все же нужна дополнительная инвалидация.
Самый простой способ программная инвалидация по ключу - реализовать инструмент для ручного запуска админами обновления в кеше измененной записи.

#### Сравнение с другими методами инвалидации 
Временная инвалидация - не подходит, так как важна актуальность данных, а если TTL короткий, будут часто случаться кеш-промахи, и кеширование в таком случае окажется неэффективным.
Инвалидация по запросу также не поможет при ручных апдейтах данных в бд.
